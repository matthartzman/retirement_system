# Multiple plans per user on the multi-user server: design

Status: approved (owner decisions recorded in section 11; implementation in progress)

Scope: let one user of the multi-user server keep several plans (a base case and what-if scenarios), each private to
that user. Builds on `multi-user-server-plan.md`, `multi-user-server-gateway-design.md` and
`multi-user-server-security-review.md`. Resolves the plan-count and disk-quota part of review item P7-O5.

## 1. What already exists (Phase 1 findings)

The single-user app already has a **plan registry**; the server needs far less new code than "multi-plan" suggests.

| Piece | Where | State |
|---|---|---|
| Registry (`plan_registry` table: `plan_id`, `path`, `name`, `kind` user/demo/case, `last_opened`) and the one-row `active_plan` table, both in the per-user `app.db` | `src/stores/app_store.py`, `src/plan_registry.py` | Exists. Per-workspace, so already per-user. |
| Every plan is its own `.rpx` SQLite file; `active_plan_path()` and `workspace_context.active_plan_id()` resolve through the registry | `src/active_plan.py`, `src/workspace_context.py` | Exists. |
| `GET /api/plans`, `POST /api/plans/switch`, `rename`, `forget` | `src/server/plan_routes.py:2394-2450` | Exist and are `ALLOWED` in remote mode (`remote_allowlist.py:131-134`). |
| Upload as base64 JSON (`mode: open`) writes `saved_plans/<safe stem>.rpx`, registers it and activates it | `plan_file_service.upload` | Exists: a user can already accumulate many plans by uploading. |
| Download of the **active** plan as `.rpx` | `plan_file_service.download_active` | Exists. |
| Header plan switcher (a `<select>`; switch only) | `frontend/js/dashboard_decomp_plan_switcher.js` (81 lines) | Exists. No create, rename, duplicate or delete UI. |
| Registry paths in remote mode must lie inside the workspace (`resolve()` based, so a junction out is refused) | `plan_registry._require_inside_workspace`, `remote_mode.is_inside_workspace` | Exists. |
| Demo plan = `demo.rpx`, kind `demo`, fixed id `demo` | `demo_plan_service.py` | Exists. |

What reads "the plan" already goes through the active plan, so switching needs no change:

- **Build subprocess**: `plan_db_env()` pins `RETIREMENT_SYSTEM_PLAN_DB`, `..._PLAN_ID` and the revision at build start; outputs go to `output/plans/<plan_id>/`. A switch during a build does not redirect the running build.
- **Result snapshots, cash view, year-end**: keyed by `active_plan_id()`.
- **YTD tracking**: three tables inside each plan file (`ytd_tracking.py` header), read through `workspace_store(root)`, which is the active plan for the live workspace. A what-if plan therefore has its own YTD data (a copy of it, if duplicated).
- **Current Snapshot / Financial Insight reporter hooks**: `financial_trends_reporter/*` all go through `active_plan.workspace_store(base_dir)` or `peek_plan_data_for_input_dir`, so they follow the active plan. The reporter is disabled in remote mode (shared-state inventory, section 5), so this only matters if it is enabled later.

### What assumes exactly one plan (the real gaps)

1. **No way to create a new plan beside the current one.** `POST /api/plan/blank` (Start New Plan) clears the active plan after a backup. `save-as` and `load-file` take a server path and are refused in remote mode (`_SERVER_PATH`). Only upload creates a second plan.
2. **No duplicate.** Needed for what-if cases.
3. **No delete.** `forget` only drops the registry row; the `.rpx` stays in `saved_plans/` forever, still counting toward disk, unreachable by the user. `forget` is a leak in remote mode.
4. **No caps.** Plan count and disk are unbounded (P7-O5). An upload is bounded to about 48 MiB per request, but nothing bounds the number of uploads.
5. **Display names are unchecked.** `rename` accepts any non-empty text (length, control characters, bidi marks, duplicates).
6. **Backups only know `plan.rpx` and `app.db`.** `gateway/backups.py:_copy_user` and `backup_store._USER_MEMBERS/_MEMBER_RE` hard-code those two. Restore replaces `app.db` (the registry) but cannot bring back the other plan files, so after a restore every other plan shows "file missing". **This is a data-loss bug as soon as users hold more than one plan, and it already affects users who uploaded a plan.**
7. **Migration of `plan.rpx` is fine.** The first run registers `plan.rpx` (`_bootstrap`), so an existing single-plan workspace is already "one registered plan"; no data migration is needed.
8. **Active plan is per worker, not per browser tab.** Two tabs of one user share the active plan, as in the desktop app. Accepted (section 4).
9. **Gateway proxy and allow-list need no structural change**: the gateway forwards by path to the user's worker; the allow-list is per route.

## 2. Plan identity and naming

- **Plan id**: server-assigned `uuid4().hex` (32 hex characters), generated by `AppStore.register_plan` (already its default). The client never proposes an id. Existing plans keep the ids they have (`plan`, `demo`, ids from `file_plan_id`); they match the same `validate_plan_id` pattern.
- **Display name**: user text, shown only; it is never used in a path. Normalised on create, duplicate and rename: Unicode NFC, control characters and bidi override characters removed, whitespace collapsed, trimmed, 1-60 characters. Names are unique per user, case-insensitively: create and duplicate append " (2)", " (3)" to a clash; rename refuses a clash with a clear message.
- **File location**: new plans are written to `<workspace>\plans\<plan_id>.rpx`. The name never reaches the file system, so there is nothing to sanitise, collide or traverse. Existing files (`plan.rpx`, `demo.rpx`, `saved_plans\*.rpx`) stay where they are. Upload keeps writing `saved_plans\<sanitised name>.rpx` (sanitised and made unique by the server, as before); it only gains the limit checks.
- **Every operation takes `plan_id` only** and resolves it through the user's own registry. An id that is malformed, unknown, or belongs to someone else yields the same response: `400 {"success": false, "error": "That plan was not found."}`. The registry is per-user `app.db`, so another user's ids simply do not exist in it.
- Every registry path is re-checked inside the workspace (`resolve()`, so junctions and `..` are refused) on every use, as today.

## 3. Operations

New or changed routes (all need an entry in `remote_allowlist.py`, the route manifest, and the allow-list tests):

| Route | Behaviour |
|---|---|
| `GET /api/plans` | Unchanged shape, plus `limits` (`max_plans`, `plan_count`, `disk_used_mb`, `disk_quota_mb`) so the UI can disable New/Duplicate and explain why. |
| `POST /api/plans/create` `{name, from: "blank"\|"demo"}` | Copy the shipped demo seed to `plans/<id>.rpx` (same step `remote_worker.provision` uses), apply `blank_plan_rows` for `blank`, register kind `user`, activate, run `_after_plan_switch`. Count and quota checked first. Nothing is touched if any step fails (temp file then rename). |
| `POST /api/plans/duplicate` `{plan_id, name?}` | SQLite backup-API copy (`copy_sqlite_file`) of the named registered plan to `plans/<id>.rpx`; default name "<name> (copy)"; stays on the current plan (owner decision 3). |
| `POST /api/plans/rename` | Unchanged route; adds the normalisation and uniqueness rules above. |
| `POST /api/plans/delete` `{plan_id}` | Refused for the active plan, the demo plan, a plan with a running or queued build, and the user's last non-demo plan. Otherwise: unregister, delete the file and its `-wal`/`-shm` sidecars, delete `output/plans/<id>/`, all after confining each path. Irreversible, so the UI confirms with the plan name. Audit event `plan_deleted`. |
| `POST /api/plans/forget` | `REFUSED` in remote mode with the reason "leaves an orphaned file counting toward your quota; use delete". The desktop app keeps it. |
| `POST /api/plans/switch` | Unchanged. Refuses a plan whose file is missing. |
| `GET /api/plan/download` | Gains an optional `plan_id` (default: active) so a non-active plan can be exported without switching. Same registry resolution. |
| `POST /api/plan/upload` | Unchanged contract; stores at `plans/<id>.rpx`; count and quota checked before the file is stored. |

Switching, deleting and building are serialised by a worker-wide lock around the registry (the registry already uses `_LOCK`), so a delete cannot race a switch.

## 4. Active-plan model

Unchanged: one active plan per worker, held in `app.db`, and every read, write, build, snapshot and report resolves it through `active_plan_path()` / `active_plan_id()`. A build captures the plan path, id and revision at its start and is unaffected by a later switch. A second tab sees the switch on its next load; the existing "unsaved changes" prompt in the switcher covers the same tab. We deliberately do **not** add a per-request plan header: it would touch every route and give the gateway a new thing to validate for no benefit to a single-user-at-a-time workflow.

## 5. Per-user caps (resolves the plan-count and quota part of P7-O5)

Gateway configuration (command-line flags beside `--worker-memory-mb`, with matching fields in the supervisor's `WorkerConfig`):

- `--max-plans-per-user N` (proposed default 10; 0 means unlimited). Counts registered plans of kind `user` and `case`, not the demo.
- `--user-disk-quota-mb N` (proposed default 1024; 0 means unlimited). Counts the whole user workspace (plans, outputs, backups the worker keeps, uploads), not following links.

Delivery: the supervisor passes them to the worker as `RETIREMENT_SYSTEM_MAX_PLANS` and `RETIREMENT_SYSTEM_USER_DISK_QUOTA_MB` (same mechanism as `RETIREMENT_SYSTEM_BUILD_POOL_MAX`, `supervisor._launch_spec`). They are not in the `FORBIDDEN_ENV` set; a user cannot set them because workers get a fixed environment. The worker enforces them in one module (`src/plan_limits.py`): `check_can_add_plan(extra_bytes)` raises a typed error that routes turn into HTTP 409 with a plain message ("You have 10 plans, the limit. Delete one first.").

Enforced at: create, duplicate, upload (open and restore), and build start (refuse when the workspace is already over quota, so builds cannot be used to fill the disk). Not enforced on ordinary plan edits (a plan file does not grow meaningfully by typing). Disk usage is computed by a bounded walk of the workspace and cached for 30 seconds; the check is a guard, not an accounting system, and the surrounding disk-level protections of the operations design still apply.

## 6. Builds, hooks and YTD

No code change is needed beyond the tests in section 9. The mechanism, restated so it is pinned by tests: builds read `plan_db_env()` captured at start; result snapshots, cash view and year-end use `active_plan_id()`; YTD and the reporter hooks read `workspace_store(root)` which is the active plan. The one new rule is delete: it is refused while a build holds that plan (`BuildJobService.has_running()` is worker-wide today, which is a safe and simple refusal condition: "wait for your build to finish").

## 7. Backup and restore of all plans

Current archive: members `users/<id>/plan.rpx` and `users/<id>/app.db` plus `gateway.db`. Proposed:

- **Archive format v2.** Manifest `version: 2`. A user's members are `users/<id>/app.db` plus `users/<id>/<rel>.rpx` for **every registered plan file inside that user's workspace**, where `<rel>` is the workspace-relative POSIX path (`plan.rpx`, `plans/<id>.rpx`, `saved_plans/<name>.rpx`). The demo plan is not backed up (reproducible from the seed). `saved_plans/auto_backups` is not backed up (it is the app's own backup copies).
- **Which files**: the gateway opens the user's `app.db` read-only, reads `SELECT path FROM plan_registry`, and for each path re-verifies on its own (it never trusts the user-writable registry): resolves inside that user's workspace, suffix `.rpx`, regular file, no reparse point (`fsguard.has_reparse_point`). Anything failing is skipped and recorded in the manifest as `skipped`, never fatal.
- **Strict member-name check** on restore: `^users/(\d+)/(app\.db|(?:plan|plans/[0-9a-f]{32}|saved_plans/[A-Za-z0-9 ._()-]{1,90})\.rpx)$`, plus the existing refusal of anything else, so a hostile archive cannot write outside the workspace.
- **Restore (one user)**: as today (authenticate the whole archive first; refuse while the worker runs; stage; move the current files aside as `*.before-restore-<stamp>`; swap; roll back on any error) but over the whole member set. Plan files in the user's workspace that are not in the archive are moved aside too, so `app.db` and the plan files always come from the same moment.
- **Compatibility**: a v1 archive restores exactly as today (two members). A v2 archive is refused by an old gateway (new `version`), which is the right behaviour.
- **Restore drill** (add to the runbook): restore into a scratch data root, start a worker, `GET /api/plans`, and require every plan `exists: true`, the active plan switchable, and one build succeeding. Also test the cross-user guarantee: restoring user A never touches user B's folder (existing test) and a v2 archive holding crafted names is refused.
- **Cost**: archive size scales with the plans a user keeps. With the default quota the worst case per user is the quota; the operations design's retention and disk estimates should be rechecked (open item for the owner, section 11 question 5).

## 8. Migration of existing single-plan workspaces

None required. A workspace with only `plan.rpx` has it registered as the single user plan (`_bootstrap`); a workspace that uploaded files already has registry rows for them. After deploy:

1. Existing plans keep their paths and ids; only new plans use `plans/`.
2. The v1-to-v2 backup change takes effect at the next scheduled backup; the first v2 set is the first one that protects uploaded plans. Take a manual backup (`ops backup`) right after deploy.
3. Orphans left by the old `forget` (files in `saved_plans/` with no registry row) count toward the disk quota. `GET /api/plans` reports their total as `orphan_mb`; the operator can remove them with the existing per-user tooling. (Automatic cleanup is deliberately not done: it deletes user data.)

## 9. Isolation tests

New tests follow the patterns of `tests/test_multi_user_isolation_*_integration.py` (gateway with two users, real workers, slow tier) and the in-process style of `test_remote_snapshot_restore_confinement_regression.py`. Names (type suffix, no tracking ids):

- `test_multi_plan_isolation_integration.py` (two users through the gateway, slow tier): A cannot list, switch to, rename, duplicate, delete or download B's plan id (same uniform error whether the id exists for B or not); crafted ids (`../x`, `..\\x`, `plan`, `demo` of B, 33-char, unicode, device names `CON`, `NUL`) are rejected without touching disk; B's plan id supplied to A's `download?plan_id=` returns nothing; A cannot overwrite B by uploading with B's file name or id; A's `delete` leaves B's files byte-identical; the id of a plan A deleted returns the uniform error.
- `test_multi_plan_confinement_regression.py` (in process, remote mode on): a registry row whose path escapes through `..`, an absolute path to another workspace, or a junction/reparse point is refused by switch, download, duplicate, delete and backup; names with path separators, `..`, trailing dots, reserved names, and 10 000 characters never reach the file system (the stored file is always `plans/<hex>.rpx`).
- `test_multi_plan_service_functional.py`: create (blank and demo), duplicate (independent data after the copy; YTD tables copied), rename rules, delete rules (active, demo, last plan, running build refused), switch updates the active plan used by `build_read`, `plan_db_env` and `workspace_context.active_plan_id`, a build started before a switch keeps its original plan.
- `test_multi_plan_limits_functional.py`: count cap and quota each refuse create, duplicate, upload and build start with 409 and change nothing; zero means unlimited; the env vars arrive in the worker from the gateway flags; the demo is not counted.
- `test_gateway_backup_multi_plan_functional.py`: v2 archive holds app.db plus every registered plan and excludes the demo and `auto_backups`; a registry row pointing outside the workspace is skipped; restore round-trips all plans byte-for-byte; a crafted v2 member name is refused; a v1 archive still restores; restoring A leaves B untouched.
- `tests/test_remote_allowlist_*`: the new routes are `ALLOWED`, `forget` is `REFUSED` with its reason; `route_manifest` and the system diagram regenerated.
- Frontend (Node vm sandbox, no source grep): `planSwitcherHtml` renders New/Duplicate/Rename/Delete controls, disables New and Duplicate at the cap, and builds the right request bodies.
- The three existing isolation modules stay green; the elevated per-account run stays the owner's.

## 10. Implementation outline (Phase 3, after the owner answers)

Small commits, test first each time:

1. `src/plan_limits.py` and gateway flags, supervisor env, with unit tests.
2. Name normalisation plus the new `plan_registry` operations (create, duplicate, delete) and the `plan_file_service` upload path change.
3. Routes, allow-list, manifest; `forget` refused in remote mode; `download?plan_id=`; `limits` in `GET /api/plans`.
4. Backup archive v2, strict member regex, restore of the whole set, runbook drill.
5. Frontend: extend the switcher with a small "Manage plans" menu (New, Duplicate, Rename, Delete); stay inside the `frontend/js` size ratchet by putting the new code in a new module and removing the equivalent lines elsewhere, never by raising the ceiling.
6. Isolation and confinement tests; `fast_gates.py`; regenerate the system diagram; wi015 baseline is re-recorded only if the nav changes (it should not: this is header UI, not a nav step).

Effort (relative): steps 1-3 moderate, step 4 moderate (touches the audited backup code), step 5 light-to-moderate, step 6 heavy only because the integration tests start real workers (slow, Windows-flaky: run each once). Roughly two to three 5-hour sessions in total; check `/usage` as it runs.

Not verifiable without an elevated or installed build: the per-account isolation run, real Windows junction behaviour under a dedicated worker account, and the Job Object disk behaviour. Those stay the owner's.

## 11. Owner decisions (recorded)

1. **Limits**: 10 plans and 1024 MiB per user, configurable in the gateway config; checked on create, duplicate, upload and build start.
2. **No copying of plans between users.** A user can download a `.rpx` and send it themselves.
3. **UX**: a "Manage plans" menu beside the header plan switcher; no new nav step (the wi015 baseline is untouched). **Duplicate stays on the current plan** and does not switch to the copy (this replaces the "activates the copy" line in section 3).
4. **Delete**: hard delete with a typed-plan-name confirmation; the nightly backups still hold it.
5. **Backup size**: accept archives that grow with every plan: back up all registered plans, archive format v2, old v1 archives still restore; the plan cap bounds the size.
